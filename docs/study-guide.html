Study guide · updated Fri 30 Oct 2026

How the tester works, one piece at a time

Give it a URL. It explores the app, writes tests, drives a real browser with an AI agent, and decides pass or fail only from evidence the agent cannot fake. Tests that pass are replayed later with plain Playwright and no AI at all.

AI / LLM involved Deterministic (Playwright, no LLM) Pass Fail Warning, skipped or waiting
The 30-second version

Teams already have Playwright suites, but those run against mock data. This tool tests the real app in real time. The core idea: AI writes and repairs tests, Playwright replays them. And because AI agents happily say "done" when they are not, a separate judge checks the page, URL, network, console and screenshots before anything counts as a pass.

Chapter 01 · orchestration

The pipeline

A run is a LangGraph state graph with four nodes: crawl → plan → one runTest branch per test → writeReport. LangGraph's Send creates the parallel branches; each branch appends its result to shared state through a reducer.

Why a graph? The steps, the state they share and the fan-out are explicit and drawable (npm run graph emits this diagram from the code). Each node is a plain function, so it is testable on its own.

Chapter 02 · discovery

Crawl

Before planning, a small breadth-first crawl visits the app: same origin only, a page cap, and it never clicks links that look destructive (logout, delete). For each page it records the title, headings, buttons, forms, API calls it saw, and any test ids or hints. That site map is what the planner is allowed to talk about.

Why? A planner with no map invents URLs and button labels. Early runs failed on guessed paths like /presentation. Now the planner may only use URLs and endpoints the crawl actually saw.

Chapter 03 · test design

Plan

An LLM turns the site map (plus your one-line description) into test cases. Each test has a plain-English goal and expectations: machine-checkable statements about the end state. The goal is for the agent; the expectations are for the judge. You can also skip the planner: pass one --goal, or a committed suite file.

// one planned test (src/core/types.js → TestCase)
{
  "id": "cart-total",
  "title": "Cart total follows the quantity",
  "goal": "Add the Mug, set quantity to 3, open the cart",
  "expectations": [
    { "kind": "url", "pattern": "/cart" },
    { "kind": "text-visible", "text": "Total: $36.00" },
    { "kind": "no-console-errors" }
  ]
}

Hard (deterministic)

  • url
  • text-visible
  • selector-visible
  • api-call
  • download
  • text-appeared (toasts)

Soft (AI reads pixels)

  • visual: a yes/no question answered from a screenshot timeline

Used only when nothing deterministic can express the outcome.

Guards (regressions)

  • no-console-errors
  • no-network-failures
  • web-vitals
  • no-a11y-violations
  • theme-conformance

Rules the planner follows: prefer hard checks; a "change" question must compare before and after; never stack conditions in one question; take the shortest path (use sample content) unless the test is about creating it; only reference URLs, endpoints and test ids the crawl saw.

Chapter 04 · the key idea

Run: agent, replay, heal

The first time a test runs, a Stagehand AI agent drives the browser. If the judge passes it, every action is recorded as JSON steps with stable selectors. Next time those steps are replayed by plain Playwright: zero LLM calls. If a replayed step breaks (the UI changed), the agent takes over from that exact point and the recording is updated. That's a heal, and every heal is logged in the report.

Interactive · choose a situation, then play

Is the app actually working?

    Why it matters: AI agents are slow and cost tokens on every run; Playwright is fast, free and repeatable. This gets AI flexibility for authoring and Playwright speed for regression runs. A recording is tied to a fingerprint of the test, so editing the test's goal or expectations forces a fresh recording.

    "Healing can hide regressions, so a heal never decides the verdict. The agent's outcome is provisional; the judge overwrites it from evidence. With --no-heal a broken step is just a failure, which is what CI wants."

    Apps behind a login

    Real apps need a login. The run logs in once, before anything else, with plain Playwright, and every test starts with that session. The AI never sees the password.

    Animated · one login, shared by every test
    .envAIE2E_USERNAME · AIE2E_PASSWORD

    Sessioncookies + localStorage
    Crawler + testsstart logged in

    Press Play.

    • Finds the form itself: username and password fields, including "email, Next, then password". Unusual logins give exact steps with {{username}} and {{password}} placeholders.
    • Proves it worked: expected text, an expected URL, or by default "the password field is gone". A failed login stops the run with the reason and a screenshot, instead of failing every test the same confusing way.
    • Why not a shared browser profile? Chrome locks a profile to one browser, and tests run in parallel. Instead cookies are added to each test's browser and localStorage is restored by a script that runs before the app's own code.
    • The agent is told not to log out: every test shares the session, so one logout would break the others.

    Chapter 05 · timing

    Settle: wait until the app goes quiet

    Real apps keep changing after a click: spinners, streaming AI text, late fetches. Taking evidence too early gives wrong verdicts. settle() polls every 150 ms and only returns once, for a whole quiet window, the URL and visible text length are unchanged, nothing has aria-busy="true", no fetch/XHR is in flight, and the page isn't empty.

    Chapter 06 · the heart of it

    The strict judge

    The judge is our own code. It reads evidence the harness collected itself: the final URL, the live DOM (through Playwright), network calls, console errors, downloads, toasts and screenshots. Only visual checks call an LLM. Four rules make it strict:

    1. Never trust a success claim. The agent saying "done" counts for nothing.
    2. Vacuity. A check that was already true on the start page proves nothing and isn't counted. If no outcome check is truly earned, the test fails as Inconclusive.
    3. Asymmetric trust. If the agent says it failed and the only proof of success is an AI reading screenshots, the test fails. Hard evidence still overrides the agent.
    4. Execution errors are not failures. A crash is error, not fail, so you know whether to blame the app or the harness.
    5. Visible matches only. Text and selector checks ignore hidden copies (filter({ visible: true })). Apps keep hidden duplicates in closed menus and off-screen slides, and the first match in the DOM is often one of them.

      Theme conformance

      The themes an app ships (light, dark, brand themes) live in its production CSS as custom properties. This audit discovers them from the page itself, switches through each one, and checks that every element actually uses the theme. When something doesn't, it asks Chrome which CSS rule set that value.

      How a value is classified: Chrome DevTools Protocol CSS.getMatchedStylesForNode returns the declaration that won. If it uses var(--…), it's derived from the theme: fine. An author rule without a variable is hard-coded, reported with selector and file:line. No author rule at all means a browser default. Colours count as on-theme within ΔE₀₀ 2.3, the "just noticeable difference".

      On every screen a test reaches

      After each replay step and each agent step, the harness fingerprints the screen: route, open dialogs and menus, landmarks, visible test ids (never text, which AI apps rewrite every run). New screens get audited, at most 4 per test plus the final one; a screen another test already audited is reused. Stagehand waits for this callback, so the agent is paused, and in-between audits restore the scroll position.

      Across products: --theme-from

      Are all your products on one theme? One product (a design-system site, or the main app) becomes the reference: its themes are read once, every token resolved to a value. Every other product is then checked against those values, light against light and dark against dark. Values are compared, not names, because --color-primary in one codebase is --brand-primary in another. A product with no CSS variables at all is still checked, in its default look.

      Found while building it: the audit's "is this background transparent?" test matched any colour ending in 0, so an orange rgb(255, 102, 0) banner was never checked, and neither was pure red, green or yellow. Only an alpha of 0 counts as transparent now.

      Consistency across screens

      A value can pass on every single screen and the product still drift. Each audit also records how buttons, links, inputs and headings look; the run then flags looks that differ only slightly (ΔE between 2.3 and 10, radius within 2px), and elements named with data-aie2e-component that render in more than one way. Advisory: it never fails a test.

      Visual regression

      Some bugs change nothing a check can read: no text, no colour token, no behaviour. A squeezed grid, a shifted icon, a missing border. For those, the tool keeps approved screenshots (baselines) and compares every new run with them, pixel by pixel.

      • What is captured: the final screen, the final screen in every theme, and each replayed step. Separate from the screenshots people look at: animations finished, cursor hidden, toasts and other live regions hidden, data-aie2e-mask areas painted over.
      • Where baselines come from: a test's first passing run, just like recordings. After that, a change is reviewed: Approve makes it the new baseline, Reject keeps the old one.
      • Gate: --visual warn (default: shown for review) or fail (a difference fails the test, for CI). --update-baselines accepts everything from passing tests.
      Live · a real pixel diff between two drawn screens

      Three things real runs taught: pixelmatch's default tolerance (0.1) called a 16px→4px grid gap "unchanged" (a light card on white is a tiny colour difference), so the default is 0.02. Identical screenshots are byte-identical, so most comparisons skip decoding entirely (13 s → 3 s per run). And toasts made 1 run in 5 flaky until live regions were hidden: 245 of 245 comparisons stable after.

      src/visual/compare.jssrc/visual/baselines.jssrc/visual/check.jssrc/browser/session.js · visualCaptureui/src/components/TestDetail.jsx · VisualPaneltests/integration/visual.test.js
      Say it in an interview

      "Visual diffs are only useful if they're stable, so I measured that: the evaluation reruns the clean app and counts how many screenshot comparisons drift. Masks handle content that changes by design, live regions are hidden because toasts are timing, not design, and nothing becomes a baseline unless the judge passed the run."

      Chapter 09 · optional contract

      App hints

      Nothing is required, but apps that add a few attributes get faster, more exact tests. These are read by the crawler, the agent and the recorder.

      // all optional
<button data-testid="add-to-cart">Add</button>        // stable recorded selector (also data-test, data-cy, data-qa)
<section aria-busy={loading}>…</section>                // settle waits for it (a web standard)
<div data-aie2e-hint="Hover a slide to see delete">    // free text for the planner and agent
<button data-aie2e-reveal="hover">Delete</button>    // marks hover-only controls
<div data-aie2e-ignore-theme>…</div>                 // e.g. a user's own image or brand logo
<button data-aie2e-component="PrimaryButton">   // must look the same on every screen
<span data-aie2e-mask>Updated 10:41</span>            // painted over in visual comparisons

      Recording with hints: when the agent clicks, the harness looks for a unique test id on the element (or a close ancestor), then a non-generated #id. The recording stores that selector plus the XPath as a fallback, and replay uses whichever appears first. Apps with test ids also give the agent two extra tools: list test ids (hidden ones too) and act on one exactly.

      UI v2: the run in plain words (built Fri 30 Oct)

      The first UI was for developers: a list, tabs and a long log. UI v2 reads like a report for anyone, with the developer view one click away.

      Who reads what
      report.jsoninsights.js (no LLM) Summary · Journey · report.html

      Summary: a verdict sentence ("1 of 6 flows work for problem_user"), four numbers, "What is wrong" cards ranked high / medium / review / low, and a tests table with what happened in one line. Journey (per test): the pages the user went through, the stuck page in red, pages never reached dashed; steps grouped by page with big screenshots; why it failed in one sentence; screens that look different with Approve / Keep; the old tabs under "Developer details". Live: Log in → Explore → Plan → Test → Report, the live browser, the planned tests, what the plan review fixed.

      Why no LLM in the summary: the judge decides and reporter/insights.js only explains, as a pure function of the report. A summary written by an LLM could contradict the verdict and would spend tokens on a run that replayed for free. Tests stuck on the same page become one finding, and an error the page itself shows ("Error: Last Name is required") is quoted from the final page text. Checks can carry a plain-words label ("The cart holds 1 product"); the planner writes one, the judge ignores it.

      Where AI is, and is not: a model plans the tests, drives the browser on first runs and heals, answers visual questions, and, after the verdict, explains each failed test (judge/failureExplainer.js): the likely cause, whether it looks like an app bug, a problem with the test or the environment, and what to check next, shown as "AI's reading". Everything else is deterministic: crawl, login, replay, every hard check, accessibility, speed, theme, pixel diffs and the report wording. The order is the guarantee: the verdict exists before the explainer is asked, and a passing test is never sent to it.

      Who did what (Sat 31 Oct): every result stores inputs: the agent's model, engine and exact instruction, and the steps Playwright replayed with their source (suite written by a person, recording saved by the agent earlier, agent this run). The journey's filter (AI agent, Playwright, Judge) shows each part's steps and input; the suite editor is split the same way so a person can write the goal, the steps or the checks. Saving changed steps drops that test's saved recording, which would otherwise win. The New run page shows the same hand-offs before a run starts.

      Two engines for the browser agent: stagehand (default) uses Stagehand 3.7.3's agent(), limited to the models it knows. loop (AIE2E_AGENT_ENGINE=loop, experimental) is our own AI SDK tool loop: the model reads Playwright's accessibility snapshot (- button "Add to cart" [ref=e12]), acts by ref, and every action is saved as Playwright's own locator, so replay and healing are unchanged and any model id works. Stagehand 4 removed agent(), so owning the loop was the real migration.

      UI stack: React 19, Tailwind v4 with theme tokens as CSS variables (light/dark, no flash on load), Radix UI primitives for selects, tabs, switches and dialogs, sonner for toasts, yet-another-react-lightbox for screenshots. The standalone report.html shows the same verdict and findings with no dependencies.

      Reference

      Glossary

      Expectation
      A machine-checkable statement about the end state (URL, text, API call…). The judge's input.
      Vacuous check
      A check that already passed on the start page, so it proves nothing about the test.
      Baseline
      Snapshot of the page before the agent acts: text, URL, request count.
      Settle
      Waiting until URL, text, aria-busy and in-flight requests are all quiet for a window.
      Recording
      The JSON steps of a passed run, replayed by Playwright with no LLM.
      Fingerprint
      Hash of a test's definition. If the test changes, its old recording is ignored.
      Heal
      The agent finishing a test after a replayed step broke; logged and judged like any run.
      Trace
      The run log: every agent or replay step with the screenshot taken after it.
      Quality gate
      off / warn / fail: what quality signals do to the verdict.
      Advisory check
      A check shown as a warning under gate warn; it never changes the verdict.
      Send (LangGraph)
      Returns a list of branches to run in parallel, each with its own input.
      Reducer
      How parallel branches merge into shared state; here, appending results.
      CDP
      Chrome DevTools Protocol. Used for the screencast and for finding which CSS rule set a value.
      CSSOM
      The browser's object model of loaded stylesheets; where themes are discovered.
      Baseline
      (visual) An approved screenshot later runs are compared with. Not the same as the start-page baseline above.
      Mask
      data-aie2e-mask: an area painted over before comparing, for content that changes by design.
      CIEDE2000 / JND
      A perceptual colour-difference formula; ΔE₀₀ ≤ 2.3 is about the smallest difference people notice.
